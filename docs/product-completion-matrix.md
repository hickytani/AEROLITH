# Product completion matrix

**Assessment date:** 2026-10-22  
**Scope:** observed implementation in this repository, including the uncommitted Milestone 5 working tree.  
**Authority:** this is the single capability/status matrix for product completion. Historical sprint notes remain as dated evidence, not current status claims.

## Status and priority meanings

- **Implemented / partially verified:** code paths exist and focused evidence covers only the stated boundary.
- **Conceptual:** geometry or relationships communicate packaging intent; they do not establish physical function.
- **Missing:** no implementation was found for the stated capability.
- **P0:** prerequisite trust/data-integrity work; **P1:** essential supported-family engineering/product gap; **P2:** expand domains or product operations after foundations; **P3:** optional capability after validated use cases exist.

## Dependency graph

1. Versioned shared system and parameter contracts.
2. Canonical unit normalization, source provenance, and reviewable requirement acceptance.
3. Domain decomposition, component identity, coordinate frames, interfaces, dependencies.
4. Parametric CAD generation with controlled regeneration.
5. Geometry-backed calculations and verification.
6. Revision-bound drawings, BOM, reports, exports and workspace presentation.
7. Browser acceptance and operational recovery.
8. Additional domain generators, each with independent engineering references.
9. Optional local model evaluation; models may propose but never control CAD or verification.

## Execution order

1. **P0: requirement data integrity:** canonical unit normalization, literal evidence, conflict handling and review before commit. A versioned quantity contract now records canonical values and original-unit evidence; continue toward broader dimensional algebra and held-out prompt evaluation.
2. **P0: shared system/revision contracts:** unify project-family storage and artifact dependency keys; add atomic multi-project persistence and migration tests before broader family growth.
3. **P0/P1: supported engineering cores:** finish independent involute/profile and reference checks, then add only analyses supported by validated source data.
4. **P1: deliverables/workspace:** complete drawing-model traceability, exporter round trips and real-browser acceptance.
5. **P1/P2: a third bounded domain:** select from an actual validated use case only after plugin contracts accept a family without core-route changes.
6. **P2/P3: deployment and local-model expansion:** only after intended use, resource envelope and held-out evaluation evidence exist.

A status becomes **complete** only when the row's acceptance criteria have evidence in automated or independently reviewed checks. A document, endpoint, generated placeholder, or passing schema test alone is insufficient.
