# Engineering methods and limitations

## Supported calculations

Inputs are millimetres, newton-metres, and revolutions per minute. API input fields are numeric and state their units; arbitrary unit-bearing values are not accepted. Requirement text extraction explicitly converts torque stated in N·mm to N·m. The external gear ratio is `z_driven / z_pinion`; pitch diameter is `module × tooth_count`; center distance is half the sum of pitch diameters. Under an explicitly stated ideal, lossless transmission assumption, output speed is input speed divided by ratio and output torque is input torque multiplied by ratio. These are algebraic kinematics and ideal torque relations, not a tooth-strength result.

The CAD boundary is an ordinary unshifted external involute spur gear with explicit pressure angle `α` (14–30°, assumed 20° when omitted), pitch diameter `d = mz`, base diameter `d_b = d cos α`, addendum radius `m(z+2)/2`, and dedendum/root radius `m(z−2.5)/2`. The flank uses the mathematical involute parameterization `x = r_b(cos t + t sin t)`, `y = r_b(sin t − t cos t)`; each flank is interpolated as an Open CASCADE spline through 17 exact involute samples (16 intervals). The root transition uses a straight radial connector from `max(r_b, r_root)` to the assumed root circle; it is not a generated cutter trochoid or fillet. The profile assumes zero nominal backlash and no profile shift. CadQuery builds an Open CASCADE extruded solid with a center bore and places the two gears at nominal pitch-center distance. `outer_diameter_mm` remains the nominal addendum-circle diameter, not necessarily the phase-dependent CAD bounding-box span. The illustrative shared bore `min(max(2 × module, 4 mm), 0.7 × minimum root diameter)` is not a shaft interface requirement. STEP preserves kernel geometry; STL tessellates it. Valid solids and visual placement do not establish correct pair contact or engagement.

## Status and evidence

The API `verification` object gives each analysis a state, summary, and evidence. Supported states are `PASSED`, `WARNING`, `FAILED`, `PARTIAL`, `UNKNOWN`, `UNTESTED`, `UNOBSERVABLE`, and `EXECUTION_ERROR`. The top-level `overall` result is `PARTIAL` for any valid design and never `PASSED`; failed implemented input checks make it `FAILED`, without asserting mechanical failure. Implemented input checks may pass without implying physical performance. Ideal kinematics are `PARTIAL`; sampled involute geometry is `WARNING`; tooth strength is `UNKNOWN`; tooth contact is `UNOBSERVABLE`; thermal analysis is `UNTESTED`; service conditions are `UNOBSERVABLE`. API execution failures carry `EXECUTION_ERROR`. No result is a simulation, safety factor, certification, or manufacturing assessment. Reports include the revision and report version. Project calculation records contain formula, substitution, units, assumptions, reference note, method version and the source revision.

## Validation

The server enforces integer tooth-count ranges (pinion 8–80, gear 8–120), module 0.5–6 mm, face width 2–60 mm, pressure angle 14–30 degrees, and finite positive torque/speed. Older persisted projects default the missing pressure angle to 20 degrees. Ratio is derived from tooth counts on edits; malformed, empty, non-finite, or out-of-range edits are rejected. Candidate CAD and profile checks finish before a revision is persisted.

## Numerical reference checks

`docs/engineering-reference-validation.md` records public references, assumptions, fixed reference values, and tolerances. API regression cases cover equal and non-divisible ratios and supported input boundaries through persisted state. CAD tests inspect vertex rings, through-bores and bounding dimensions, and reopen STEP/STL exports with Open CASCADE. These are implementation regression checks; they are not an independent standards benchmark or evidence of gear strength, contact, fatigue life, tooth engagement, manufacturing suitability, or safety.

The component preview uses CAD-generated STL coordinates in millimetres with one Three.js scene unit per millimetre. Component endpoints bind the response to the generating component and revision, identify STL/mm, and return the artifact SHA-256. The UI verifies the digest and finite triangle data before adding a mesh. Camera FIT uses the union of visible mesh bounds. Mesh validity and placement do not validate physical contact; the gears remain the sampled-profile educational implementation described above.

## Known gaps

No validated tooth-contact/interference or contact-ratio checks, shaft or support design, cutter-generated root fillet, material properties, standards-based bending/contact stress, fatigue, thermal behavior, solver, uncertainty, or independent profile benchmark is included. Do not use these artifacts for manufacture or real-world design decisions.

## Generated assembly relationship checks

`assemblies.py` builds a typed project-response model for the exact geometry revision. It contains a stable assembly/subsystem/component hierarchy, canonical parameter references, actual component bounds/placements, explicit relationships, and checks carrying a check version, design and geometry revision, rule, expected/observed values, units, tolerance, evidence, and limitations. Pydantic validation rejects duplicate IDs, missing component/parent/relationship references, unknown parameter refs, hierarchy cycles, inconsistent source spans, and mismatched design/geometry revisions. `PASSED` maps to `MATCH` only for the named rule; `FAILED` maps to `MISMATCH`; `EXECUTION_ERROR` maps to `ERROR`. The overall assembly remains `PARTIAL` while any relevant physical relationship is outside the model.

For spur gears, checks inspect the generated CadQuery assembly children and Open CASCADE solids. They measure solid validity and positive finite volume, actual root/tip/profile-start radii, sampled flank vertices against the independent polar involute equation, actual axial bounds against face width, assembly origins against nominal center distance, and transform axes/phase. The ideal ratio remains `PARTIAL`; tooth contact/interference remains `UNOBSERVABLE`. These geometry checks do not establish conjugate motion, operating contact, load capacity, or manufacturing suitability.

For the EV envelope family, checks inspect generated solid bounding centers and dimensions for tire/rim/hub stack alignment, wheel and axle-reference placement, left/right frame-rail symmetry, and whole-assembly containment. Front and rear crossmembers are checked against their wheelbase-fraction locations, and Open CASCADE Boolean intersection volume is measured against each rail; this proves geometric overlap only, not a joint or load path. Propulsion-to-frame mounting and clearance checks remain `UNOBSERVABLE` because the model lacks mounting datums and fit rules. Range, structural, crash, dynamics, thermal, safety, and roadworthiness remain outside scope.

The API response exposes these results as `assembly_verification`; its `revision` and `geometry_revision` must match the canonical snapshot. Geometry verification is recomputed for each new revision. EV edits regenerate the full 27-component family before the existing compare-and-swap commit; gear edits invalidate revision-dependent outputs and the next response regenerates checks for the whole pair. There is no selective component regeneration. Artifact staleness remains revision-based, and retained artifacts are not silently relabeled current.

## Drawing and artifact traceability

The gear reference PDF (`gear-reference-drawing-0.3`) has visible project/family/schema/revision identity, canonical dimensions with stated reference/envelope meanings, and stable parameter record IDs for tooth counts, module, face width and pressure angle. Its PDF subject metadata records the complete parameter ID/value/unit/source/evidence map, component IDs, source revision and dimension semantics. The EV layout PDF similarly records its complete parameter record map, project/family/schema/revision and component IDs in PDF subject metadata; its visible notice remains `CONCEPTUAL ENVELOPES ONLY`. These fields identify the model snapshot used to create a drawing. They do not validate every graphical annotation or make either drawing a manufacturing definition.

Artifact index entries additionally record the canonical project ID, family/schema, source revision, all parameter IDs, canonical design SHA-256, artifact SHA-256, generator version and coarse dependency keys. Revision/hash mismatch marks an older file stale while checksum-valid retained artifacts remain downloadable. STEP/STL exports use a temporary generation path and are published only after successful generation and a source-revision check; a regression test confirms a failed STEP generation leaves the prior valid file and index unchanged. Artifact file and index replacements remain separate atomic writes, and the in-process index lock does not provide cross-process transaction safety.
