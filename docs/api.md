# Internal API reference

The API is versioned under `/api/v1`; FastAPI's interactive schema is available at `/docs` while the service is running.

| Method | Route | Purpose |
|---|---|---|
| GET | `/api/v1/health` | Service/kernel readiness. |
| GET | `/api/v1/design-families` | Read-only registered family metadata and planned areas. |
| GET | `/api/v1/project` | Canonical project revision, parameters, derived values, family verification, and typed `assembly_verification` for generated components and relationships. |
| PATCH | `/api/v1/project` | Apply allowlisted numeric parameter edits; accepted edits create a revision. |
| POST | `/api/v1/project/initialize` | Initialize a registered family with validated defaults, replacing the one active local project while preserving history. |
| POST | `/api/v1/project/demo` | Restore default demo state as a new revision. |
| POST | `/api/v1/project/interpret` | Deterministic, bounded natural-language extraction proposal. |
| POST | `/api/v1/project/change-impact` | Revision-bound, read-only impact preview for supported parameter names. |
| POST | `/api/v1/specifications/propose` | Return a versioned, reviewable spur-gear or EV packaging proposal; never mutates project state. |
| POST | `/api/v1/project/vehicle/generate` | Optimistically commit a reviewed, schema-validated EV packaging design into the shared project store. |
| PATCH | `/api/v1/project/vehicle` | Edit supported EV packaging dimensions, regenerate/verify CAD on a candidate, then conditionally commit one new revision. |
| POST | `/api/v1/learn/spur-gear/experiment` | Calculate uncommitted lesson parameters with the same deterministic gear core. |
| GET | `/api/v1/platform/openapi` | Live OpenAPI document for the developer portal; hidden from its own endpoint inventory. |

| GET | `/api/v1/export/stl` | Current-revision assembly STL. |

| GET | `/api/v1/report.pdf` | Current-revision PDF engineering note. |
| GET | `/api/v1/gear/layout.pdf` | Revision-bound, dimensioned spur-gear reference layout (not a manufacturing drawing). |
| GET | `/api/v1/vehicle/layout.pdf` | Revision-bound vector top/side/front EV envelope layout drawing. |
| GET | `/api/v1/vehicle/manifest.json` | Revision-bound component hierarchy, dimensions, transforms, interfaces and mesh references. |

| POST | `/api/v1/learning/traces` | Capture a redacted local execution trace only when collection is enabled and request opts in. |
| POST | `/api/v1/learning/traces/{id}/review` | Record an explicit local review decision. |
| POST | `/api/v1/learning/traces/{id}/curate` | Add an approved trace plus reviewed target/provenance to the curated dataset. |
| DELETE | `/api/v1/learning/traces/{id}` | Move raw trace to ignored local quarantine. |
| GET/POST/PATCH | `/api/v1/models/registry...` | Read registry, register checksummed candidate metadata, and apply controlled lifecycle transitions. |
| POST | `/api/v1/models/registry/rollback` | Reactivate recorded previous approved local runtime model. |
| POST | `/api/v1/engineering/tools/validate-proposal` | Validate an allowlisted, revision-bound tool proposal; never executes it. |

PATCH body fields: `pinion_teeth` (8–80 integer), `gear_teeth` (8–120 integer), `input_torque_Nm` (>0), `input_speed_rpm` (>0), `module_mm` (0.5–6), `face_width_mm` (2–60), and `pressure_angle_deg` (14–30; default 20° for older/missing values). Unknown fields are rejected. The gear ratio is derived from tooth counts. Gear geometry is rebuilt from the sampled involute profile and validated before the revision is persisted. A successful edit returns the complete new design state. Validation errors use FastAPI's structured HTTP 422 response.

`POST /api/v1/specifications/propose` is read-only and returns source prompt, canonical parameter targets, exact prompt spans where text was parsed, units, limits, component dependencies, assumptions, unresolved values, conflicts and unsupported scope. Gear proposals expose pressure angle as user-provided evidence or an explicitly assumed 20° default. Gear proposals map to the existing `PATCH /api/v1/project` contract; EV proposals map to `POST /api/v1/project/vehicle/generate`. Acceptance includes the revision that was reviewed. Unsupported requested systems are surfaced separately; the UI may accept only the supported conceptual geometry slice and labels it partial. Duplicate contradictory values, incompatible units, parameter-range failures, and cross-field failures do not produce a committable proposal. The original prompt and accepted parameter evidence are retained in the canonical project. Gear project responses expose component-to-parameter traceability. The EV manifest and BOM include each generated component's canonical parameter references and value/source/evidence records; the source prompt and SHA-256 are included where supplied. EV subsystem associations remain conceptual and do not establish physical interfaces. The EV family shares the same single project file and history with the gear family.

PATCH `/api/v1/project/vehicle` requires `expected_revision` plus at least one supported field; unknown fields are forbidden, values must be finite, and cross-field constraints are validated before CAD generation. Supported fields and units/bounds are `overall_length_mm` (>1500–12000), `overall_width_mm` (>800–4000), `body_height_mm` (>800–3000), `wheelbase_mm` (>1000–8000), `front_track_mm` and `rear_track_mm` (>800–3000), `tire_outer_diameter_mm` (>300–1500), `tire_width_mm` (>100–600), `ground_clearance_mm` (>50–500), `frame_rail_width_mm` (>20–300), `frame_rail_height_mm` (>20–400), `body_width_mm` (>800–4000), and `body_length_mm` (>1000–12000). Ranges are in millimetres and upper bounds are inclusive. Wheelbase plus tire diameter must fit inside overall length; tracks/tire widths must fit overall width; body and tire clearance rules also apply.

The project response exposes `editable_parameters` with current value, source/evidence, units, bounds, step and affected components. An overall-length edit links the body envelope length to the new overall value and scales an assumed wheelbase proportionally. An overall-width edit adjusts assumed front/rear tracks and assumed body width to preserve the package envelope; when an edited tire width requires it, assumed tracks and body width are propagated to preserve clearance. Any propagated value stays explicitly `ASSUMED` with evidence; an explicit edited value becomes `USER_PROVIDED`. Other parameters drive the components listed in each field's dependency metadata. User-provided dependent values are not silently changed; incompatible candidates are rejected with HTTP 422.

The endpoint builds a complete candidate, checks stable identities and valid/nonzero Open CASCADE solids, evaluates wheel/axle centers, rail dimensions and overall-envelope containment, then uses a process-local revision compare-and-swap before saving. HTTP 409 means the project changed during regeneration; 422 means the candidate did not validate; a geometry execution error returns 500. Rejections preserve canonical state and revision. The response lists regenerated component IDs, artifact IDs made stale, and no artifact files as regenerated: exports remain on-demand. Old artifact records/files are retained and marked stale by revision; current artifacts carry the new design revision, `cq-ev-envelope-0.2` generator version, SHA-256 and named parameter dependencies. The local service remains single-process/single-writer across the full application; this route's compare-and-swap prevents an in-process stale candidate commit but does not add multi-process safety.

The project response's typed `assembly_verification` includes family/schema and generator versions, stable assembly/component hierarchy, canonical parameter/provenance references, relationships, and evidence-backed checks. Each check records its identifier/version, design and geometry revision, parameters/components, deterministic rule, expected/observed values, units/tolerance, evidence, and limitations. Pydantic rejects missing references, hierarchy cycles, and revision mismatches. The overall assembly result remains `PARTIAL`; `PASSED` is scoped to one named check and is not an aggregate functional-assembly result.

Gear checks inspect the actual generated CadQuery assembly solids and transforms for profile root/tip vertices, positive solid validity/volume, nominal center placement, axes/phase, and shared face width. Tooth contact remains `UNOBSERVABLE`. EV checks inspect generated CAD for wheel/rim/hub concentric envelope placement, axle references, rail symmetry, crossmember/rail Boolean overlap, component validity and declared outer-envelope containment. Boolean overlap is not a joint-strength result. Propulsion/frame mount fit, clearance and load paths remain `UNOBSERVABLE` or `PARTIAL` because datums and interface criteria are not modeled. Range remains a target, not a calculated outcome. The EV geometry remains conceptual, not safety, performance or production engineering. EV exports include STEP/STL, per-component STL, PDF layout, manifest and BOM JSON. The learning experiment route does not persist supplied parameters.

Verification uses the existing states `PASSED`, `FAILED`, `PARTIAL`, `UNKNOWN`, `UNTESTED`, `UNOBSERVABLE`, `WARNING`, and `EXECUTION_ERROR`. For the milestone's requested vocabulary, `PASSED` is a `MATCH` only for the specific named, evidence-backed check; `FAILED` maps to `MISMATCH`; `EXECUTION_ERROR` maps to `ERROR`. Overall vehicle verification remains partial because several physical checks are outside the model. No aggregate `MATCH` is emitted when checks are unknown, partial, skipped, or stale.

The geometry route accepts an optional `revision` query parameter. If it differs from the canonical revision, or the project changes while tessellation is running, the API returns HTTP 409 with the current revision in `X-Design-Revision`; it will not return a mesh from a different revision under the requested identifier. Successful component mesh responses use `model/stl`, `Cache-Control: no-store`, and carry `X-Geometry-Component-ID`, `X-Geometry-Revision`, `X-Geometry-Units: mm`, `X-Geometry-Format: stl`, `X-Artifact-ID`, and `X-Artifact-SHA256` alongside generator/version headers. The browser verifies these fields and the bytes before constructing a Three.js mesh. Experiment request fields match the gear parameters and use the same numeric bounds as the project model; invalid input returns HTTP 422 and does not create a project revision.

Gear and EV layout PDFs carry project/family/schema identity and source revision in their title/header and PDF metadata. The gear sheet visibly maps key stable parameter IDs; PDF subject metadata for both families contains the complete parameter record IDs, canonical values/units, provenance/evidence and component IDs. Layout drawing artifacts are indexed against the source design hash and parameter IDs and become stale after edits. The gear drawing is a reference sheet marked not for manufacture; the EV drawing is conceptual envelope output. Neither is a validated manufacturing definition. STEP/STL artifacts are published only after generation and a current-revision check; API tests reopen gear STEP/STL through Open CASCADE and verify a failed STEP generation preserves the prior indexed artifact.

The local Platform page derives its endpoint inventory from the live OpenAPI document instead of maintaining a separate route list. Local API access has no authentication; do not expose this single-project, single-writer service as a public multi-tenant API. API-key issuance and hosted services are not implemented.

Model extraction is disabled unless `AEROPKMECH_ENABLE_MODEL_EXTRACTION=true` and a loopback Ollama model is configured. `/api/v1/model/status` checks service reachability and the exact model tag but marks `inference_tested: false`; only an actual schema-valid answer is reported as `INFERENCE_SUCCEEDED`. `POST /api/v1/components/explain` uses the active registry model, if one is approved, or `AEROPKMECH_OLLAMA_MODEL`; absent/unavailable inference falls back to deterministic component context and exposes a bounded failure status. Model responses cannot mutate project state or execute validated tool proposals. Training capture requires both `AEROPKMECH_ENABLE_TRAINING_CAPTURE=true` and `opt_in: true`; captured data is redacted and remains raw/unreviewed until explicitly approved and curated. See [model strategy](model-strategy.md) for training isolation and current hardware limits.

Local quick start:

```powershell
npm run dev
Invoke-RestMethod http://127.0.0.1:8000/api/v1/project
```

PATCH requests may include any non-empty subset of `pinion_teeth` (integer 8–80), `gear_teeth` (integer 8–120), `module_mm` (0.5–6), `face_width_mm` (2–60), `pressure_angle_deg` (14–30), `input_torque_Nm` (>0), and `input_speed_rpm` (>0). An optional `expected_revision` makes the edit conditional on the revision the user reviewed; a mismatch returns 409 without changing the project. A successful edit increments `revision` once and returns new calculations/verification with that revision. Candidate CAD/profile checks run before persistence; a 422 leaves prior persisted state unchanged. Multi-process writers remain unsupported.

Numeric requirement proposals include an additive versioned quantity envelope: schema version, quantity kind, canonical value and unit, source class, original input value/unit and conversion factor when available, evidence/source span, derivation and supported bounds. Existing project numeric fields and request bodies remain canonical and unchanged. Both family states persist synchronized quantity records and stable parameter records. A parameter ID is stable as `project_id:canonical_path`; its record binds the quantity/provenance to a family, project revision, and related component IDs or source parameter IDs. Existing records without the additive maps migrate deterministically during schema validation; inconsistent saved records are rejected. Artifact index entries include project/family/schema identity and parameter IDs, while prior artifacts remain retrievable and become stale after a project revision change. Revision-conditional commits use same-directory atomic replacement and an in-process compare-and-swap. Separate processes are not coordinated and remain unsupported.
