# Engineering intelligence and model strategy

The requirement intake uses deterministic patterns for one fully generated family and a conceptual electric-vehicle architecture outline. For a spur gear pair it records matched text as evidence, validates the supported numerical ranges, identifies missing fields and detects a stated gear-ratio conflict with explicit tooth counts. Complete reviewed values can be committed through a revision-conditional PATCH. For the narrow electric road-vehicle path it extracts seats, dimensions, range, and electric intent, then returns a conceptual subsystem hierarchy; each node says no geometry generator is available, the artifact list is empty, and no design can be committed. No defaults are filled from the active project.

`RequirementProvider` is the replaceable asynchronous provider interface. Future LLM results must return only the typed proposal, pass Pydantic validation, and remain a user-reviewed proposal. Model output cannot run code or commands and cannot set calculation/verification results. Deterministic calculations stay authoritative.

There is no model training or remote inference configured. The Studio identifies deterministic pattern extraction and does not present it as a language model. Training would be premature without permissioned inputs, independent outcome labels, a held-out evaluation set and a demonstrated benefit over this baseline. Private project data is not collected for training. Planned evaluation should include schema validity, omissions and conflicts, question quality, revision edit success, numerical consistency, unsupported-claim rate and failure handling.
