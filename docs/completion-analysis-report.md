## 1. Executive assessment

AeroPKmech is a runnable, local web demonstrator for one constrained design family: an educational external spur gear pair. It connects a Next.js/React shell and Three.js viewer to a FastAPI backend. The backend owns typed project state, input validation, revisions, deterministic calculations, CadQuery/Open CASCADE geometry and exports, requirement text proposals, and HTML/PDF reports.

The core demonstration flow works end to end: read the current project, propose fields from supported text, let a user edit inputs, persist a new revision, recompute values, view component meshes, and request current-revision CAD/report files. The initial baseline recorded **7 passing tests**. The engineering-integrity sprint subsequently expanded the suite to **35 passing tests**, with a successful Next.js production build.

This is a bounded educational prototype, not a validated gear-design or production engineering system. The tooth shape is a polygonal approximation, not an involute; the calculations are ideal kinematics; material strength, contact, thermal behavior, safety, manufacturing tolerances, and independent engineering validation are outside the implemented scope. The default intake is deterministic, and a local-only model adapter now exists for optional, uncommitted proposals and component answers. **No successful model inference or training run has been established.**

## 3. Application flow and state behavior

1. `npm run dev` starts the API on `127.0.0.1:8000` and Next.js on `127.0.0.1:3000`. The web app proxies API and local static/vendor assets to the API service.
2. FastAPI reads `data/project.json` as the local canonical project. The current family contains a pinion and a driven gear.
3. `GET /api/v1/project` returns stored state with current deterministic derived values and validation issues.
4. `POST /api/v1/project/interpret` returns a typed, uncommitted proposal. The extractor does not infer missing values from the demo project defaults.
5. A user may apply supported numeric values through `PATCH /api/v1/project`. The backend retains the old full state in history, derives ratio from tooth counts, advances the revision, and saves the candidate state.
6. The viewer requests current component STL meshes from the API. The CAD kernel, not the browser, creates the meshes.
7. Assembly STEP/STL and HTML/PDF reports are produced on request from the current project state. CAD and PDF responses identify the revision; CAD responses also identify the CAD generator version.

State and outputs are local files. There is no database transaction layer, file locking, artifact catalog, immutable object store, or stale-artifact dependency graph. Two concurrent writers or a crash during a write have not been addressed as production concerns.

## 4. Engineering analysis

### 4.1 Supported model

The current demo starts from an 18-tooth pinion and 54-tooth gear, module 2 mm, face width 12 mm, input speed 900 rpm and input torque 8 NÂ·m. For this state:

- Ratio is `54 / 18 = 3:1`.
- Pitch diameters are `2 mm Ã— 18 = 36 mm` and `2 mm Ã— 54 = 108 mm`.
- Pitch-center distance is `(36 + 108) / 2 = 72 mm`.
- Under the ideal lossless assumption, output speed is `900 / 3 = 300 rpm`.
- Under that same assumption, output torque is `8 Ã— 3 = 24 NÂ·m`.
- Outer diameters use the implemented approximation `module Ã— (teeth + 2)`.
- A shared bore is selected by `min(max(2 Ã— module, 4 mm), 0.7 Ã— minimum root diameter)`. This is visible as an unverified illustrative assumption, not a specified shaft fit.

The output torque relation ignores losses and does not calculate tooth forces or stress. A 3:1 ratio result is a kinematic relation, not a rating that the modeled gear can carry 24 NÂ·m safely.

### 4.2 Geometric construction

Each gear boundary uses four polygon vertices per tooth, alternating root and tip radii. Root radius is `module Ã— (teeth âˆ’ 2.5) / 2`; tip radius is `module Ã— (teeth + 2) / 2`. The polygon is extruded by face width, with a central bore. The pair is placed at the sum-of-pitch-radii distance. This yields real Open CASCADE solid objects and real STEP/STL files, but it does not produce a conjugate involute tooth profile. Visual placement does not establish correct tooth engagement or operation.

### 4.3 Validation applied

The implementation constrains pinion teeth to 8â€“80, driven gear teeth to 8â€“120, module to 0.5â€“6 mm, face width to 2â€“60 mm, and input torque/speed to positive values. It checks stored ratio consistency and finite center distance. CAD tests check solid validity, positive volume, and face-width bounding dimension at minimum and maximum supported cases. API integration coverage checks a representative revision edit, invalid module rejection, CAD export signatures, report responses, component mesh, and local web/Three.js asset responses.

These checks establish code-path and geometric-kernel behavior for the tested inputs. They do not validate meshing, loads, durability, standards compliance, numerical agreement against an independent reference, or real-world suitability.

## 5. Requirement text handling and AI status

The default parser recognizes a narrow set of expressions for pinion and driven-gear tooth counts, ratio, torque, speed, module, and face width. It handles explicit NÂ·mm torque conversion to NÂ·m, derives ratio from explicitly stated tooth counts, records matched text evidence, flags a conflicting stated ratio, validates against a strict Pydantic proposal schema, and lists missing values. Optional loopback Ollama extraction can propose the same gear schema when explicitly enabled; every proposal remains uncommitted and requires user review.

The optional `OllamaProvider` is restricted to loopback. It provides model status, component-context answers, and opt-in gear extraction with schema validation, bounded context and deterministic fallback. It does not mutate state or execute tools. There is no remote inference, document/image/PDF parser, or open-ended specification understanding. Training is not evidenced as complete and should not be described as complete.

## 9. Security, reliability, and usability boundaries

- The service binds to loopback in the included launcher; it is not ready for public exposure.
- No login, authorization, tenant isolation, CSRF defense, rate limit, or privacy/retention control is implemented.
- Project state is a single JSON file. Durable database transactions, backup/restore, concurrent edits, and multi-project workflows are absent.
- CAD generation is synchronous and has no isolated worker, resource quota, background job queue, or operational monitoring.
- Exports are revision-named and indexed with checksums; historical artifacts remain retrievable and are labeled stale after a design change. Artifact file and index updates are separate atomic writes, not one transaction.
- Requirement parsing can miss valid phrasing or match a narrow supported phrase incorrectly. Its evidence and confirmation status help make the result reviewable; they are not a guarantee of semantic correctness.
- The interface is a single-family demonstrator. Advanced component editing, assemblies/mates, clearances, constraints, variants, undo/redo, comparison, and traceability are absent or planned.
