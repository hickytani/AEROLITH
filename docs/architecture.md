# Architecture and canonical state

The application separates a Next.js/React presentation service from a FastAPI domain API. Next.js proxies versioned API and legacy Studio assets to FastAPI. FastAPI/Pydantic own schemas, revisions, deterministic engineering calculations, and verification summaries. CadQuery/Open CASCADE generate the assembly solids and CAD exports. `public/app.js` fetches current-revision component STL data, checks component/revision/unit/format and SHA-256 provenance in `public/mesh-loader.js`, then parses and validates it before Three.js scene insertion. `public/camera-fit.js` calculates camera poses from the visible scene bounds. These browser modules do not create CAD or own engineering calculations. `data/project.json` is the local source of truth; an accepted edit retains the old state in history and writes a new monotonically increasing revision. The full candidate is Pydantic-validated before an atomic same-directory temporary-file replace. Revision-conditional commits compare the source revision under a process-local lock, require exactly one revision advance, and preserve the active project ID across family changes. Failed writes leave the previous state file intact. Separate processes still have no shared lock or multi-writer guarantee.

The project store keeps one active revision at a time and supports `spur_gear_pair@1.0` and `electric_vehicle@1.0`. Gear calculations and CAD remain family-specific. Both family schemas expose the shared `EngineeringQuantity` and `ParameterRecord` contracts without forcing their domain models together. Stable parameter IDs use `project_id:canonical_path`; each record snapshots schema, family, revision, unit/source evidence, and component/source-parameter relationships. The family validators build these records for legacy state lacking them and reject unknown schema versions, dangling component/source references, or inconsistent values/revisions. The EV family holds typed, provenance-tagged packaging dimensions and builds 27 separately identified CadQuery solids for a conceptual body/frame/wheel and propulsion-envelope assembly. `PATCH /api/v1/project/vehicle` supports the generator-backed geometry dimensions; overall-envelope changes have explicit propagation rules for assumed wheelbase, tracks and body dimensions. The endpoint validates a candidate, regenerates CAD and geometry checks, then uses a process-local compare-and-swap before save. Both families share the same atomic project file, revision history, artifact index, and stale revision behavior. EV target range is not a calculated outcome.

The prompt-to-CAD path starts at `POST /api/v1/specifications/propose` and remains read-only until explicit user acceptance. Typed proposal parameters identify their canonical target, units, accepted bounds, exact source span when a literal was parsed, and affected components. Known unsupported systems, contradictory repeated values, invalid units, and cross-field constraints remain explicit rather than being silently accepted. Gear acceptance writes through the existing revision-conditional gear PATCH; EV acceptance writes through the existing revision-conditional generation request. Both persist the source prompt and user evidence in the same canonical design revision. EV component manifests and BOM entries reference the generator-backed canonical parameters with their value/provenance; associations that are only packaging intent remain labelled conceptual. The Studio clears prompt evidence from any value edited during review so the accepted value cannot retain a stale quote.

Engineering checks use `verification.py`'s established states. A `PASSED` check is equivalent to `MATCH` only for its named criterion; `FAILED` corresponds to `MISMATCH`, and `EXECUTION_ERROR` to `ERROR`. Partial interface, unknown strength/range, and unobservable properties remain separate; the system does not emit an aggregate match when required evidence is missing or incomplete. `assemblies.py` builds the `/api/v1/project` `assembly_verification` record from actual family generator outputs. Its typed hierarchy, relationships, dependencies and checks are validated for stable references and matching design/geometry revisions. Gear checks measure generated solid profile rings, bounds and assembly transforms; EV checks measure actual wheel stacks, axle placement, rail symmetry, crossmember/rail Boolean overlap and declared envelope bounds. Each rule records expected and observed values, units/tolerance, check version, evidence and limitations. The overall assembly remains `PARTIAL`; unsupported tooth contact and physical EV mounts remain `UNOBSERVABLE`. The Studio filters these real relationships/checks to the selected component and displays their revision and evidence.

CAD and report outputs are generated from one loaded `Design` snapshot per request. Each output is atomically written under a filename containing its revision and generator/report version, then recorded with a checksum, project/family/schema identity, and stable parameter IDs in `artifacts/artifact-index.json`. The gear family also exposes a two-view reference-layout PDF with explicit reference dimensions and non-manufacturing caveats. `GET /api/v1/artifacts` lists metadata and marks records stale when their revision differs from the current project. `GET /api/v1/artifacts/{filename}` allows retrieval of retained prior outputs, verifies the checksum, and reports stale state in a response header. Current export routes always generate from the current snapshot. Historical outputs are retained as local files; there is no background job or object store.

This remains a constrained local architecture. PostgreSQL, authentication, artifact recovery, and multi-process write coordination are future work. EV artifact records now include named parameter dependency keys, while revision remains the authority for stale status. Keep model-provider adapters separate from deterministic calculations. The requirement provider protocol accepts only validated typed proposals and never executes model-generated code.

## Optional local model and training boundary

`model_platform.py` provides a loopback-only Ollama provider for selected-component explanations and optional gear extraction. It receives bounded canonical project context, validates model output, checks that the revision stayed current, and falls back to deterministic responses. All proposed tools are allowlisted and revision-bound with `executed: false`; they require user confirmation and are not dispatched by this adapter. `ModelRegistry` stores checksummed candidate metadata and enforces candidate/evaluated/approved/active transitions and rollback. The active registry model takes precedence over the explicitly configured local baseline.

Training capture is disabled unless both the local setting and request opt-in are present. The raw trace is redacted and starts unreviewed; review and curated target entry are separate. Raw traces, curated examples, weights, caches, and registry state are excluded from Git. `ml-training/` is a separate Linux/WSL CUDA environment; no model dependency is installed into the API runtime. The small checked-in v2 JSONL set is synthetic development data, not a useful domain corpus. No successful inference, adapter training, candidate evaluation, or model activation has been recorded. See [model strategy](model-strategy.md).

## Design-family contract

`services/api/aeropkmech/families.py` defines the `DesignFamily` contract and registry. A family provides stable identity, schema, capabilities, limits, artifacts, validated defaults/state, calculation, verification, and geometry generation. Gear calculations/CAD delegate to `engineering.py` and `cad.py`; EV intake, typed state, assembly solids, vector layout, manifest and BOM are in `automotive.py`. Unknown family identifiers and unsupported schema versions return HTTP 422. EV geometry is an envelope study, not production engineering.

`GET /api/v1/design-families` is authoritative for the New Design flow. `POST /api/v1/project/initialize` initializes the registered family with validated defaults and advances the one local project's revision while retaining its old state in history. It is not multi-project storage. `POST /api/v1/project/demo` restores the demo defaults as a new revision. Family registration itself does not create a revision or regenerate artifacts.

## Calculations and learning

Project responses include calculation rows with formula, substitution, assumptions, reference note, method version, status, and design revision. The provenance revision matches the project snapshot used for the calculation and verification response. `POST /api/v1/learn/spur-gear/experiment` runs supplied lesson parameters through the same deterministic gear engineering module without saving them; its provenance identifies an uncommitted experiment and the canonical source revision. Lesson completion is stored in versioned browser `localStorage` only. No cross-device progress sync or connected tutor is implemented. `TutorProvider` is an integration seam; the shipped lesson explanations and calculations remain deterministic and authored.

## Learn and Platform

The App Router exposes `/learn`, `/platform`, and `/designs/new`; Studio remains `/`. Learn contains the implemented gear lesson and uses the experiment endpoint. Platform reads the live FastAPI OpenAPI document at `/api/v1/platform/openapi`, displays actual versioned endpoints and schemas, and provides copyable local examples. There is no hosted API, account system, public key issuance, billing, or public deployment security boundary.
